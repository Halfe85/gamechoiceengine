# Game Choice Engine – story graph v1

A mobile companion for branching narratives. **First supported content:** *Game of Thrones: A Telltale Games Series*, episode 1 chapter 1 **partial prototype**.

## Event-first model

`episode → scene/chapter → node → option → effect → state variable → goal rule`

`nodes.kind` covers `story`, `dialogue`, `action`, `decision`, `qte`, `check`, `inventory`, `quest`, and `transition`. A node has zero or more selectable responses. Nodes need not be decisions; they can represent instructions or automatic events. Storyline flags are stored as effects. The schema already defines condition groups/terms and option-scoped event transitions, as well as partial dialogue turns and mechanic checks; the first UI prototype still navigates its sample nodes sequentially. Quest objectives can be linked to nodes.

**Game profiles:** `telltale` for timed dialogue and QTE; future adapters may add skill/dice systems without changing the story model. Game-specific roll results should be entered by the player, not generated by this companion.

**Evidence:** Only verified effects may color decisions as supporting/conflicting with an ending. Unmapped or speculative outcomes remain unclassified. A requested "best possible ending" is not guaranteed by this draft.

## Build

Run `python3 database/build.py`. It writes:
- `public/data/game.sqlite` — generated canonical SQLite game content.
- `public/data/game-of-thrones.json` — read-only projection for the initial Angular browser client.

The Angular workflow runs this Python build before bundling. Later, the same SQLite file can be consumed by SQLite WASM, with the player's private separate database persisted via OPFS.

The current prototype saves manual progress in localStorage and does **not** claim SQLite browser persistence yet. Data cleared from the browser may be lost. Only one early chapter is partially populated: six episodes are defined, but later episode content is NOT yet implemented.

## Content strategy

1. Expand **episode 1 chapter 1** to every verified dialog beat, examination, action, QTE, and key consequence.
2. Populate and execute conditional edges, skipped-dialogue options, timed responses, and automatic quest-completion criteria.
3. Continue with the other five chapters of episode 1, then the remaining episodes.
4. Extend profiles for BG3 dice rolls, DC checks, retries and conditional quest state.

Sources are listed in the generated database, and prose is editorial paraphrase rather than copyrighted script transcription.


## Exact dialogue contract

**No paraphrased/invented game dialogue.** The tracker only renders dialogue with
`dialogue_turns.verification='verified'`, a non-empty exact on-screen
`prompt_text`, a known source, and `exhaustive=1`, alongside every response
from `dialogue_options` verified with an individual source. If any part is missing,
the UI instead shows **Exact dialogue not verified**; no fake choices can be clicked.

For each *actual* on-screen dialogue prompt, create one turn (or ideally a separate
dialogue story node if it branches into unique state), in its original language and
with the same capitalisation, punctuation, option order, and displayed silence choice.
The dialogue choice's *on-screen label* goes in `dialogue_options.screen_text`,
not the generic `options.label` used for non-dialogue actions.
The character's actual **spoken response** and subsequent NPC lines may be recorded
separately in ordered `dialogue_replies`, each requiring its own source.

The initial Episode 1 dialogue placeholders are deliberately **pending**. Prior
generic examples such as "Answer confidently" were removed instead of being
presented as actual in-game lines. Exact textual content needs a verified,
permitted source, such as gameplay screenshots/transcriptions supplied by the user
or other properly licensed material. We don't bulk-copy third-party game scripts.

Dialogue progress is stored per turn, independently from the node completion.
Navigation and legacy save-state fallback remain supported.
